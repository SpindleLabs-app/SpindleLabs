# Account

Contents of `packages/account`: optional sign-in. The rules are in packages/CLAUDE.md and the root CLAUDE.md. Accounts are optional forever: nothing in CAD or slicing may ever wait for, or depend on, an account or the network. Keep this list current when you add or change a file here.

- `config.ts`: `checkConfig` checks the account service's address (https, or http only on this computer for tests; no path, query or user name), its public key and the app's return address. With no config the app has no sign-in and contacts nothing.
- `pkce.ts`: the RFC 7636 secret and its S256 challenge (checked against the RFC's own worked example).
- `session.ts`: the session kept in localStorage and the checks on every token reply. Only the user's id, email and name are kept (no picture); a damaged or wrongly shaped value is refused whole.
- `auth.ts`: `authClient(deps)`: `state()` (no network), `beginSignIn()` (the Google sign-in address), `finishSignIn(pageUrl)` (swaps the returned code once, refuses a code with no matching secret from this browser or one older than 10 minutes, and gives the address without the code), `accessToken()` (refreshes within 60 s of running out; a refused refresh signs this browser out; offline keeps the session), `signOut()` (local at once, then ends this session at the service). `asPersonFunction(path, body)` calls a server function (under /functions/v1/) as the person. Plain fetch, no library; never throws.
- Tests: `test/fake-service.ts` fakes the service's four requests with its own SHA-256, so PKCE is checked independently; `test/auth.test.ts` covers forgery, cancelling, reuse, the 0.9×/1.1× boundaries of both time limits, every failure kind, broken storage, two tabs refreshing, and 60 seeded sessions against a plain model.
- `data.ts`: `accountData(client)`: `emailChoice()`, `setEmailChoice(yes)`, `myData()`, `deleteAccount()` through the client's `asPerson` (the data API as the signed-in person, token refreshed first); answers are checked, and a failed delete keeps the session. `PENDING_EMAIL_KEY` holds a yes ticked before sign-in until the return. `SEEN_EMAIL_KEY` (`<user id>:yes|no`, given the store) keeps the last email choice read or saved, so the account dialog shows it at once (`lastEmailChoice()`, null for another person or a damaged value) and the service's answer then puts it right; signing out and deleting the account forget it (`forgetEmailChoice()`). `plan()` reads the plan; `checkout(monthly|yearly, returnTo)` and `manage(returnTo)` give a Stripe page's address (only ever checkout.stripe.com or billing.stripe.com); `deleteAccount()` goes through the billing function (ends any subscription first) and falls back to the database's own delete, which refuses while payments are linked. Tested against the fake service's data API in `test/data.test.ts`. `test/billing.test.ts` tests the server's billing function (supabase/functions/billing) against a fake Stripe and Supabase: signatures (0.9×/1.1× of the 300 s tolerance), test mode only, checkout prices and coupon, no second subscription, stale events, deleting with Pro.
- `words.ts`: `FAILURE_WORDS`, a plain sentence for every way a sign-in or request can fail.
- `designs.ts` (My designs): `designsApi(client)`: `list`, `get`, `save`, `remove`, `removeAll`, `space`, `keeping`, `setKeeping`, every answer checked against the shapes the database gives (`rowFrom`, `saveAnswerFrom`); `SOURCES` and `LIMITS` must match the migration (checked by `test/designs.test.ts`). Account features 2: `versions(id)` (times, newest first) and `version(id, at)` (file text or null) read the account's earlier versions (`LIMITS.versionsKept`, `versionGapMinutes`, checked against the versions migration).
- `sync.ts` (My designs): `designSync(deps)` links each project in this browser to one design (`LINKS_PREFIX` + user id, in localStorage): `syncAll` sends projects whose text's SHA-256 changed, naming the revision last seen; another device's newer save keeps this browser's as "<name> (copy)"; a design deleted from the account is never sent back; too big waits until it changes; full stops the round; `firstTime`/`firstChoice`/`leftCount`/`includeLeft`: nothing is sent before the person says the projects already here are theirs; `bring(remote)` puts a design into this browser without ever overwriting a change made here. `test/fake-designs.ts` answers as the migration does; `test/sync.test.ts` (hand-worked two-browser cases, 60 seeded sessions against a model).
- `settings.ts` (settings that follow you, account features 3): `settingsApi(client)`: `read` (`my_settings`), `save(settings, expected)`, `setKeeping(on)` (off deletes the account's copy), answers checked (`accountSettingsFrom`, `saveSettingsAnswerFrom`); `SETTINGS_LIMITS` must match the migration. `mergeSettings(specs, base, local, remote, prefer)`: a three-way merge per setting ("map": per JSON entry; "list-by-id": the slicer presets per id, the later `updatedAt` winning; a change always beats a deletion; settings not in `specs` keep the account's value). `settingsSync(deps)`: `round()` reads, merges against the base this browser and the account last agreed on (`SETTINGS_BASE_PREFIX` + user id; none: the account's value wins), saves naming the revision (a crossed save merges again, `SETTINGS_TRIES`), and writes the merged values here except one changed meanwhile; too big is held and not resent until it changes; `changedHere()` reads storage only. `test/fake-settings.ts` answers as the migration does; `test/settings.test.ts` (hand-worked merges, two-device rounds, 0.9×/1.1× of the size limit, failures, 5 seeded random three-device runs against a last-writer model).
- `shares.ts` (sharing links, community C2b): `sharesApi(client)`: `share(name, body, picture)` (answers shared/too-big/full/daily), `open(id)` (anyone, signed in or not, through the client's `asAnyone`: the person's token when there is one, else the public key alone; never says who shared it), `list`, `unshare`, `report(id, kind, reason)` (kept/gone/enough/bad); every answer checked (`shareRowFrom`, `shareAnswerFrom`); `SHARE_LIMITS` and `REPORT_KINDS` must match the migration (checked by `test/shares.test.ts`). `test/fake-shares.ts` answers as the migration does; the SQL itself is checked by `supabase/test/test_shares.py`.
- `names.ts` (community C6b): `namesApi(client)`: `mine()` (name, `changedAt`, `nextChangeAt`; null with no name) and `set(name)` (one of `NAME_ANSWERS`), answers checked; `nameWords` says each refusal, `nameDate` spells the day out; `NAME_LIMITS` must match the migration (checked by `test/names.test.ts`). `test/fake-names.ts` answers as the migration does (look-alikes folded by a short key).
- `likes.ts` (community C7b): `likesApi(client)`: `count(id)` (anyone, through `asAnyone`; null when the link is off, taken down or never was, or sharing is off), `mine(id)`, `like(id)` (one of `LIKE_ANSWERS`), `unlike(id)` (one of `UNLIKE_ANSWERS`); never who liked; answers checked; `LIKE_WORDS` says each refusal; `LIKE_LIMITS` and both answer lists must match the migration (checked by `test/likes.test.ts`). `test/fake-likes.ts` answers as the likes migration does on top of `fake-shares.ts` (held accounts, the switch, the daily cap, likes deleted with a link turned off); `test/likes.test.ts` (hand-worked counts, the cap at 0.9× and 1.1×, 60 seeded sessions against a set model); `test/share-likes-app.test.ts` checks the app's `likeParts` (apps/fission src/share.ts).
